# Modules métier

Chaque module vit dans `apps/server/src/modules/<module>/`, possède le schéma PostgreSQL du même nom et n'expose que son `index.ts`. Les dépendances listées sont des appels synchrones à la façade publique d'un autre module ; les réactions asynchrones passent par les événements de domaine (outbox). Le `README.md` de chaque module détaille les événements qu'il émettra (indicatifs).

Le graphe des dépendances synchrones doit rester acyclique. Aucun module n'a besoin de dépendre de access pour protéger ses routes : `@Public`, `@RequireAction` et `@CurrentPrincipal` sont des métadonnées de `platform/http` appliquées par le garde de access (ADR 0015). Un module ne dépend de access que pour sa façade (rôles, niveaux de confiance) ou pour fournir des prérequis. De même, profiles ne dépend pas d'organizations : organizations lui enregistre un annuaire au démarrage (ADR 0025) ; ni de network : network lui enregistre l'écoute des vues de profil (ADR 0030). network ne dépend d'aucun module propriétaire de cible de suivi : organizations et projects lui enregistrent leur type de cible (ADR 0027). content ne dépend pas de projects : projects lui enregistre le validateur de rattachement des publications et la source des actualités du fil ; organizations non plus : projects lui fournit les projets portés. payments ne dépend ni d'access ni d'organizations pour leurs registres : il enregistre au démarrage la source du niveau `kyc_verified` et l'élément `payout_account` (access), et les projets soutenus (organizations). `notifications`, `discovery` et `privacy` lisent l'activité des autres modules par leurs événements ou leurs façades, jamais par leurs tables.

## Règles vérifiées par ESLint

| Règle                                                                                                                                                 | Outil                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Un module n'importe d'un autre module que son `index.ts`                                                                                              | `boundaries/dependencies`                          |
| `domain/` n'importe que son propre `domain/`, `platform/kernel` et `@pitchorium/contracts` (ni NestJS, ni Drizzle, ni `node:*`, ni `infrastructure/`) | `boundaries/dependencies`, `no-restricted-imports` |
| `platform/` n'importe aucun module métier                                                                                                             | `boundaries/dependencies`                          |
| Les points d'entrée (`src/*.ts`) n'importent que les `index.ts` des modules                                                                           | `boundaries/dependencies`                          |
| Un module n'importe que son schéma `@pitchorium/db/schemas/<module>`                                                                                  | `no-restricted-imports`                            |

Les tests unitaires (`*.spec.ts`), y compris dans `domain/`, peuvent importer vitest et toutes les couches de leur propre module, mais jamais les fichiers internes d'un autre module : seule la règle de pureté de `domain/` leur est épargnée. Les règles sont définies dans `packages/config/eslint-boundaries.js` ; `apps/server/test/architecture/boundaries.spec.ts` vérifie qu'elles détectent des violations volontaires.
